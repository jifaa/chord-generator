## Anti-Patterns Verdict

**LLM assessment**: The interface largely avoids AI slop. The dark cosmic theme with violet gravity/cyan tension color system is owned and deliberate — it doesn't read as generic template. Typography hierarchy (Space Grotesk display, Inter body, JetBrains Mono labels) is consistent and appropriate.

**Minor slop patterns detected**:
- **Identical 3-column card grids**: Reference page applies the same card treatment to Graph Theory, Chord Functions, Cadences, and Popular Progressions sections — all identical density, same border-radius, same padding. Sections with fundamentally different content types (theory text, tabular data, progression lists) look identical.
- **Numbered section markers (01–04)**: Landing page "Mulai Sekarang" steps use `01 · 02 · 03 · 04` format — a reflexive scaffold that appears regardless of whether the sequence order carries information. The order does carry information (sequential steps), so this is borderline defensible, but it's borderline.
- **Eyebrow text pattern**: `text-xs uppercase tracking-[0.2em]` appears on every page via PageHeader. Consistent = professional, but creates visual monotony.

**Clean elsewhere**: No gradient text, no side-stripe borders, no hero-metric template, no default glassmorphism, no text overflow, no decorative motion that breaks reduced-motion preference.

**Deterministic scan**: CLI detector returned clean across all 6 pages. Browser automation confirmed: 0 console errors, 0 horizontal overflow, 0 broken images, 0 unnamed buttons, all pages HTTP 200. The automated scan did not catch the cognitive load issues, consistency inconsistencies, or accessibility gaps that manual review identified.

**Visual overlays**: Browser visualization confirmed all pages load cleanly. No user-visible overlay findings from automated injection.

## Overall Impression

Chord Map has genuine design strength in its visual identity — the dark cosmic theme with violet/cyan chromatic system is coherent, owned, and differentiated. The Builder page's progressive disclosure flow is the best UX pattern in the product. But the score of 25/40 reflects real gaps: keyboard accessibility is a P0 blocker, the Builder's cognitive load is overwhelming for first-timers, and `alert()` dialogs break the immersion the design otherwise earns.

The **single biggest opportunity**: keyboard accessibility on Explorer (ChordGraphCanvas) and Genre selection (LineSidebar). Fix those two and you eliminate the WCAG A compliance gap and open the product to Sam (screen reader users) and Alex (power users who want keyboard navigation).

---

## What's Working

1. **Builder's progressive disclosure flow** — The step-by-step structure (choose root → get suggestions → add next → repeat) creates genuine empowerment. Users feel in control while guided. The progress bar builds anticipation and the completion celebration (PartyPopper + "Progression Selesai!") delivers a genuine emotional peak. This is the product's best UX pattern.

2. **Visual identity cohesion** — The dark cosmic theme with violet gravity (#7c5cfc) and cyan tension (#22d3ee) is applied consistently across all 6 pages. Typography hierarchy is clear. Component vocabulary (Panel, PageHeader, SpecularButton) is consistent. The product has visual personality, not decoration.

3. **Genre sidebar proximity interaction** — Despite accessibility issues (zero keyboard nav), the LineSidebar's proximity-based genre highlighting creates a satisfying tactile feel that differentiates the product. Musically relevant genres highlight when adjacent to the selected one. This is a clever, domain-specific interaction pattern.

## Priority Issues

### [P0] Keyboard accessibility: ChordGraphCanvas and LineSidebar
- **What**: Explorer page ChordGraphCanvas (WebGL canvas) and Genre selection LineSidebar have zero keyboard accessibility. No tabIndex, no role attributes, no keyboard event handlers.
- **Why it matters**: Screen reader users (Sam) cannot navigate the graph at all. Keyboard-only users (Sam and Alex) cannot select genres via sidebar. This is a WCAG 2.1 SC 2.1.1 (Keyboard) failure — a P0 accessibility blocker.
- **Fix**: For LineSidebar: add tabIndex, role="listbox" with role="option" children, arrow key navigation, and focus indicators. For ChordGraphCanvas: provide a list/table alternative view with full keyboard nav, or add arrow-key navigation between nodes with screen reader announcements.
- **Suggested command**: `/impeccable audit` (to surface all accessibility issues systematically), followed by `/impeccable harden` (to address the edge cases)

---

### [P0] Builder cognitive overload: 7+ simultaneous interactive zones
- **What**: Builder page has sidebar + count controls + custom input + progress slots + suggestion area + 4+ action buttons = 7+ interactive zones visible simultaneously.
- **Why it matters**: High cognitive load causes decision paralysis. Jordan (first-timer) will feel overwhelmed and abandon. Alex (power user) will want to speed through but can't because the interface requires scanning all zones.
- **Fix**: Collapse the count/settings into a collapsible panel. Show only the current action slot and suggestion area as the primary focus. Move secondary actions (Undo, Transfer to Generator) to a compact toolbar. Use progressive disclosure — reveal settings only when the user clicks an expand control.
- **Suggested command**: `/impeccable layout` (fix spacing/rhythm), `/impeccable quieter` (tone down overstimulation)

---

### [P1] Inconsistent border-radius on SpecularButton
- **What**: Generator's "Generate Progression" button uses `radius={12}` (squarish corners) while all other buttons use `radius={9999}` (pill shape).
- **Why it matters**: Breaks visual rhythm on the same page. Pill buttons with one squarish button feel disjointed. The design system specifies large rounded corners (16px for cards) — the button inconsistency is a standards violation.
- **Fix**: Standardize SpecularButton on `radius={9999}` (pill) across all usages. If 12px is intentional for a specific context, document it in DESIGN.md and apply consistently.
- **Suggested command**: `/impeccable polish` (fix component inconsistencies across pages)

---

### [P1] `alert()` dialogs break immersion and accessibility
- **What**: Clipboard failures trigger `alert()` in Generator (line ~117) and Builder (line ~96). This blocks the thread, applies browser-native styling (breaks the dark theme), and is inaccessible.
- **Why it matters**: `alert()` is a jarring interruption in an otherwise polished dark-cosmic interface. Screen readers announce alert dialogs as errors even when they're not. It signals "we didn't build this properly" in a way the rest of the UI doesn't.
- **Fix**: Replace with an inline toast/notification component. Use the app's existing Panel component or create a minimal toast with: icon, message, auto-dismiss (3s), and a close button.
- **Suggested command**: `/impeccable harden` (replace alert with proper error handling)

---

### [P2] Reference page: 4 identical 3-column card grids
- **What**: Reference page has 5 sections. Graph Theory, Chord Functions, Cadences, and Popular Progressions all use identical 3-column card grids. Only Roman Numerals section uses a table layout.
- **Why it matters**: Sections with fundamentally different content types look identical. Users cannot scan for structure. The page reads as "a wall of cards" rather than "a music theory reference with multiple section types."
- **Fix**: Vary the layouts — Roman Numerals table is correct. Cadences could use a 2-column list with chord symbols in mono font. Chord Functions could use horizontal cards with accent colors for primary/secondary/dominant functions. Popular Progressions could use a stacked list with copy buttons.
- **Suggested command**: `/impeccable layout` (vary section layouts), `/impeccable quieter` (reduce visual monotony)

## Persona Red Flags

**Alex (Power User)**: No keyboard shortcuts detected anywhere. Form requires multiple clicks for primary actions (Generator: select genre → select mode → click Generate, 3 steps minimum). No save/export/JSON config option. Undo is per-chord only, not session-level.

**Jordan (First-Timer)**: Builder has 7+ simultaneous interactive zones causing cognitive overload. Player page has no onboarding tooltip or guidance — "beta · bonus page" eyebrow signals internal uncertainty. Reference page is text-heavy with no guidance on where to start (which section first?).

**Sam (Accessibility)**: ChordGraphCanvas not keyboard accessible. LineSidebar not keyboard accessible. Native `<select>` on KeySelect (mode selector) differs from custom GenreButtons styling — inconsistent affordance for users with cognitive differences.

## Minor Observations

- **Shadow in a "no-shadow" system**: Design system says "no shadows — tonal elevation only" but SpecularButton uses `box-shadow: inset 0 1px 0 rgba(255,255,255,0.04), 0 8px 24px rgba(0,0,0,0.25)` — shadow is present and inconsistent with the stated system.
- **Playing state isolation**: Only the active chord button lights up cyan during playback. If the user switches tabs, no audio cue that playback stopped. Users may not realize playback ended.
- **Player input validation**: Player accepts custom chord input. "C G Am F" works but "Cmaj7 Gm7" would silently produce no sound — no validation feedback for invalid chord names.
- **"beta · bonus page" eyebrow on Player**: Signals internal uncertainty about the feature's value. Either commit to it as first-class or remove the qualifier.
- **Mixed language surface**: EN function names (I, V, vi), EN page labels (Generator, Explorer), mixed with Indonesian body text. Consistent language choice (EN or ID) should be a deliberate decision.
- **No save/share/continue at Builder completion**: The Builder celebrates "Progression Selesai!" but offers no next step — no save, no share, no "start new." The emotional peak has nowhere to go.

## Questions to Consider

1. **Is the WebGL SpecularButton worth its cost?** The shader complexity creates performance risk, bundle size overhead, and maintenance burden for what is fundamentally a styled button. Does the specular effect meaningfully differentiate the product, or is it tech showcasing at the expense of simplicity and load time?

2. **Should the Reference page be a wall of cards?** It's comprehensive but emotionally flat. Is this page serving users, or is it developer-aspirational ("look how much theory we know")? A Reference page should be scannable and lead users to what they need, not present everything equally.

3. **Where is the "save progression" feature?** Users can copy to clipboard, but there's no way to save a progression within the app. Builder celebrates completion but offers no continuation path. This is the biggest gap between "tool" and "product."

4. **Is Indonesian language a choice or an oversight?** The mixed EN/ID surface will confuse non-Indonesian musicians who encounter the product. If the target market is Indonesian musicians, this is correct. If it's global, this should be a deliberate decision with i18n infrastructure planned.
